# .ics device validation checklist (U2, epic #8)

Manual gate for the calendar integration. Run on real phones — an Android with the Google Calendar app and an iPhone with Apple Calendar — before the update/cancel UI copy ships. Record each outcome in place and commit the result with the PR.

The fixtures live in `src/modules/ics/fixtures/` and were generated by the shipped serializer (`src/modules/ics/`), so they are byte-identical to what the app emits: same UID across all three, revisions 0 → 1 → 2.

- `01-create.ics` — booked, 2026-09-15 15:00 Europe/Sofia, `SEQUENCE:0`
- `02-update.ics` — same UID, moved to 16:30, `SEQUENCE:1`
- `03-cancel.ics` — same UID, `STATUS:CANCELLED`, `SEQUENCE:2`

Get the files onto each phone however is convenient (send them to yourself in a chat app, or serve the repo folder). Import them **in order**.

## A. Import behavior (the re-import assumption)

| # | Step | Expected | Android / Google Calendar | iPhone / Apple Calendar |
|---|------|----------|---------------------------|-------------------------|
| A1 | Open `01-create.ics` | Event appears 15 Sep 15:00 with two reminders (day before, hour before) | | |
| A2 | Check the reminders on the created event | Both alarms present (Google may substitute account defaults — note what shows) | | |
| A3 | Open `02-update.ics` | The existing event **moves** to 16:30 — no duplicate | | |
| A4 | Open `03-cancel.ics` | The event is removed or visibly cancelled | | |

A3 is the plan's biggest assumption (same UID + higher SEQUENCE replaces). A silent no-op on iPhone is the documented failure mode — that outcome confirms the in-app guidance line, it does not stop the feature. **A1 failing on either platform is the plan's stop condition.**

## B. Delivery path (which tap actually reaches the calendar)

Run from the app itself (or any page serving the fixture with `Content-Type: text/calendar`) — not from a chat-app file preview.

| # | Step | Expected | Android / Chrome | iPhone / Safari |
|---|------|----------|------------------|-----------------|
| B1 | Trigger the share sheet with the `.ics` as a `text/calendar` file | Calendar app is offered as a share target | | |
| B2 | If B1 offers no calendar target: complete the download fallback and open the file | Import screen from section A appears | | |
| B3 | Count the taps from button to "event saved" on the winning path | Record the number per platform | | |

B decides each platform's primary path: if the share sheet cannot reach the calendar app on a platform, the download/open flow becomes primary there and the share sheet is not offered.
