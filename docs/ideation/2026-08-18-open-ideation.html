Ideation

What's Next for when-again

An open (surprise-me) ideation run over the whole project: codebase, docs, issue tracker, and external research. Seven ranked directions survived generation by six independent framing agents and an adversarial verification pass that opened every cited file — and, for one idea, ran a production build.

date: 2026-08-18 topic: open-ideation mode: repo-grounded 48 raw → 23 candidates → 7 survivors

Grounding Context

Codebase. 13 modules in a clean modulith — zero deep-reach import violations, zero inline debt markers (no TODO/FIXME/skipped tests anywhere), all modules unit-tested (~211 unit + 31 e2e). Debt lives as tracked issues, not code rot. shell is the outlier: 30 files / ~2,046 LOC bundling app chrome, both mode home screens, settings, and update UI — the default landing spot for every new screen because the project bans a shared/ folder. The provider-side /clients route is a bare placeholder (epic #5). No .ics code exists anywhere, despite the README promising "One tap adds it to your calendar, and the calendar reminds you."

Backlog. Four open epics, all unspecified — and two of them (#9 robustness, #10 testing/CI) largely describe work that already shipped. Untracked gaps named in specs but filed nowhere: client-mode backup v2, per-provider detail route, services-editor question, synthetic-provider merge.

External research (2026). No dedicated no-backend appointment product exists anywhere — the niche is unclaimed. Fresha killed its free tier in 2025 ($19.95/mo); Booksy has none ($29.99/mo). Google abandoned the Notification Triggers API with no replacement, so scheduled local notifications are dead as a web capability — which makes .ics calendar handoff the only durable serverless reminder path, not a stopgap. QR practical ceiling ~800 bytes. iOS push requires home-screen install + iOS 16.4+.

Verification. Every candidate's citations were checked against the live repo by fresh-context verifiers (14 sound / 6 weak / 0 refuted). Corrections they forced are folded into the cards below and flagged where they matter.

1.

Ship .ics as the product's sync channel, not an "add to calendar" button

Confidence 85% Complexity: Medium All 6 frames converged here
Description

Epic #8 is currently framed as "one button on the client home card." Reframe it as the app's only cross-device write channel. The provider's share action hands over the .ics as the shared file (navigator.share({ files }), blob-download fallback), so the OS calendar takes it and the reminder exists before the client has ever opened when-again. A stable UID derived from the appointment id plus an incrementing SEQUENCE gives mutation semantics: a reshare replaces the client's calendar entry instead of duplicating it, and STATUS:CANCELLED retracts it. Every later feature that changes an appointment (edit, cancel, reschedule) inherits a working propagation path instead of inventing one.

Basis

direct: README.md:15-16 — "One tap adds it to your calendar, and the calendar reminds you" — against zero .ics code anywhere in src/ (verified by repo-wide grep). The handoff wire format already carries everything a VEVENT needs (codec.ts:28-41: dateTime, IANA zone, duration, cancelled flag). external: Google ended Notification Triggers API development with no standards-track replacement, so scheduled local web notifications are dead; VALARM (RFC 5545 §3.6.6) is broadly honored on import by Google and Apple Calendar.

Rationale

This is the product's entire reminder mechanism and its only unbacked public promise, and the external research says it is the near-unique market position: no competitor serves the "client installs nothing" case. Framing it as transport rather than export means the reminder works with no install, no permission grant, no iOS version floor — on an ancient Android with WhatsApp and a stock calendar.

Downsides & open forks

Two genuine design forks the generating frames disagreed on, to settle in a brainstorm: floating DTSTART vs DTSTART;TZID= (floating time is the literal iCalendar encoding of the wall-clock rule; TZID is what makes the alarm fire in the client's real local time) — and whether the event DESCRIPTION carries a self-restoring re-import link, which would travel to the client's own Google/Apple account and needs a plain-language privacy disclosure rather than silence.

Verified prerequisitereceived has no revision field — only status: 'booked' | 'cancelled' — and a reshare "overwrites in place" silently. Without a monotonic revision in the payload and the row, the app can only ever emit SEQUENCE:0, and calendar clients may drop reschedule updates as duplicates (plausible but confirmed only via secondary sources — validate against real Google/Apple Calendar early). The data-layer field is a prerequisite for this epic being correct, not an enhancement after it.
Sequencing tension (verified real)Shipping this well substantially undercuts the client's reason to keep the PWA — the calendar carries the reminder. Decide client mode's standalone value in the same breath; the strongest candidate answer is the "lifelong multi-provider visit record" reframing (see Rejection Summary — folded into this decision, not lost).
2.

"Your data survives" — one release, three layers

Confidence 90% Complexity: Medium Pain · Leverage · Analogy · Flip frames
Description

Three verified defects form one story, and each alone is insufficient. (a) Eviction: requestPersistentStorage() is written, exported from db's public API, and unit-tested — and called from nowhere (verified: zero app call sites). Every provider's business record sits in default, evictable IndexedDB; WebKit caps script-writable storage at 7 days of non-use for non-installed sites. (b) Completeness & forward-compat: exportBackup hand-lists three tables, so received and savedProviders are silently absent from export and the import transaction — a client who backs up gets a file omitting their own data — and parseBackup rejects on strict version equality, so the day v2 lands, every v1 file users saved becomes unimportable. Fix structurally: each module contributes its backup slice through the same defineXStore(db) registry it already uses for schema, plus a version-upgrade ladder and frozen v1 golden fixtures now, while exactly one version exists. (c) Habit: attach backup to a "close the day" ritual (day summary → backup file as the closing act), stamping lastBackupAt on completion — which resolves the deferred stamping-contract decision (verified: the stamp currently fires before any save dialog) — and add a restore drill that parses a backup and reports its contents without writing (parseBackup is already a pure validator).

Basis

direct: db.ts:28 + zero call sites (grep-verified); backup.ts:12-19, :48, :63-73 (all verified line-exact); the stamping comment at backup.ts:27-31. external: WebKit ITP 7-day cap confirmed via webkit.org; local-first peers (Obsidian, Standard Notes) draw complaints precisely on recovery UX.

Rationale

Device death and silent eviction are the only failure modes that destroy everything with no error and no recovery — the worst possible outcome for a product whose pitch is "your data never leaves your phone." Persistence without a complete backup still loses client data; a complete backup nobody makes still loses everything; a ritual over an evictable store is theatre. Three layers, one release.

Downsides

The registry-derived backup is a format change and needs the upgrade ladder shipped in the same release. "Close the day" is a new surface that must earn its place on summary value the provider actually wants, or it becomes a nag.

3.

Re-spec epic #5 as a recall & rebook engine, not an alphabetical list

Confidence 80% Complexity: Medium 5 frames converged
Description

Epic #5's stated scope is a filing cabinet: "alphabetical client list; client page with phone tap-to-call, notes, visit history newest-first." Build the recall list instead: derive each client's personal cadence (median gap between their own visits) from history already in the database, lead the screen with "due for a visit (7)" ranked overdue-first, and make the primary control a one-tap rebook — "same as last time, four weeks out" — that writes an appointment directly, demoting the multi-screen funnel to the exception path. Alphabetical browse becomes the secondary view. A prefilled WhatsApp/SMS nudge per due client rides along as the outreach channel.

Basis

direct: _provider.clients.tsx is entirely a <Placeholder> (verified); getVisitHistory already returns non-cancelled visits newest-first; forward-looking next-visit logic exists only on the client side (clientVisits.ts:28-39) — the provider has no "who is due" computation at all. external: dental/optometry recall systems run on exactly this constraint — no push channel, revenue recovered by computing who is overdue from one's own records. The caveat is real: their interval is protocol-fixed; hair/nail cadence must be learned per client and shown as an overridable estimate.

Rationale

An alphabetical list is a screen the provider maintains; a recall queue is a screen that makes them money — and it is the one thing paper genuinely cannot do. The app is named when-again and nothing in it currently answers that question. This is the last unbuilt provider screen and no spec exists yet, so reshaping it costs nothing today and a rewrite later.

Downsides

Cadence inference needs ≥2 visits per client to say anything; the screen must degrade gracefully to the plain list for new providers. Scope is larger than the epic's current body — this is a re-spec decision, not scope creep to smuggle in.

4.

Make the handoff a two-way protocol: card, request, ack

Confidence 65% Complexity: High 4 frames converged
Description

The handoff's one-directionality is an accident of which way the QR points, not a constraint. Add payload kinds to the existing codec: card (a client hands over their own name and phone — the provider stops transcribing, and duplicate clients stop being created at the source), request (a client proposes a service and time window; the provider's inbox pre-fills the booking form), and ack (a tiny return link confirming the appointment landed). A no-tech companion: a 4-character match code derived from the appointment's canonical fields, rendered on both the provider's row and the client's card — read aloud at contact, it is a handoff receipt and staleness detection (codes differ ⇒ the client holds a pre-reschedule card). This also unlocks "your clients are your replica set": a provider whose phone died recovers their book gradually as regulars scan their copies back — recovery no competitor and no local-first tool has, using zero infrastructure.

Basis

direct: codec.ts:38 — "decode ignores unknown keys, so these are v:1-compatible both directions" (verified verbatim) — a kind discriminator ships without a version bump. The Wire interface has no client-name field (verified field-by-field), so payloads cannot yet say whose appointment they are: a cheap additive key today, impossible retroactively once payloads are in the wild. Client→provider payloads carry only an id and revision — orders of magnitude under the ~800-byte QR ceiling. external: client-initiated booking is the flagship feature Booksy/Fresha charge $20–30/mo for; LOCKSS is the honest analogy for the recovery path (regeneration, not restore — lazy, partial, only the clients who return).

Rationale

"Did they get it?" is the provider's real anxiety and the reason paid tools sell delivery receipts. Doing requests, receipts, and disaster recovery with no server converts the architecture's apparent weakness into its moat — and the protocol change is one codec seam feeding three features.

Downsides

Largest design surface of the seven: an inbox UI, new payload kinds, and honest UX about what recovery can and cannot restore (never the provider's notes or prices). Do the additive client-name key early even if the rest waits.

5.

Stop shipping the provider app to clients on first load

Confidence 90% Complexity: Low Constraint-flip frame · verified by real build
Description

The verifier ran npm run build and confirmed it: dist/index.html unconditionally modulepreloads the schedule chunk (121.8 KB) and booking chunk (80.1 KB) for every visitor — provider-only code a client can never reach — because the / route's Home() component statically imports both ClientHome and ScheduleScreen and branches at runtime on settings.mode. TanStack Router's autoCodeSplitting is already on and already splits per-route; it cannot split a runtime branch inside one file. The fix is small and precise: React.lazy the two branches inside Home() (and audit the preload hints), then add a CI size budget on the client entry so the property is a ratchet, not a one-time cleanup.

Basis

direct: zero lazy/import( hits in src/app/ (verified), autoCodeSplitting: true at vite.config.ts:46, and the build-output evidence above — stronger than the original candidate claimed, with the diagnosis corrected by the verifier.

Rationale

The client's first load is the most fragile moment in the product — worst device, worst network, zero motivation, one shot — and it currently downloads ~200 KB (pre-gzip) of unreachable code. The "client installs nothing" differentiator is undermined by making them download the provider application. And it matters more once idea #1 ships: when the calendar carries the reminder, first-load weight becomes nearly the entire client experience.

Downsides

Almost none — a lazy boundary adds one loading state to the mode branch. The cheapest item on this list relative to its payoff.

6.

Make the hard constraints executable: CI gates for the rules that are prose today

Confidence 85% Complexity: Low 3 frames converged
Description

Every architectural invariant lives in Markdown and is enforced by whoever happened to read it. Encode the checkable ones: no-restricted-imports zones per module (index-only imports, dexie allowlist), import/no-cycle, grep gates for dark: variants / a hardcoded /when-again/ / a shared/ folder, a test pinning listClients's localeCompare sort (the documented "do NOT clean up" Cyrillic trap), and — the verifier's sharpened remainder — a check on the main.tsx string-table composition (a module registered in en but not bg typechecks fine today) plus a glossary gate for cross-module drift: "Отменен" vs "Отказан" for cancelled is live right now across three string files. Per-module key parity is already tested in CI; these two gaps are what remain.

Basis

direct: boundary audit clean repo-wide as of 2026-08-18 — true and unenforced; the glossary drift verified at shell/strings.ts:129 / handoff/strings.ts:62 vs schedule/strings.ts:72. reasoned: this repo's stated process is subagent-driven implementation, so the effective contributor count is unbounded and none of them remember a spec comment from three weeks ago. A rule that exists as prose has a per-agent violation probability; a gate makes every future agent-written PR safe by construction.

Rationale

The cheapest moment to make an invariant executable is while it still holds — it locks in a property instead of recovering one. Pairs naturally with reconciling epics #9/#10 down to their real remaining scope (both verified as largely shipped), so the repo's map matches its territory in both directions.

Downsides

Lint-config surface and occasional false positives; the glossary gate needs a small curated term list to avoid becoming noise.

7.

Decide what shell is: mode as the module seam — or no mode at all

Confidence 55% Complexity: High 2 frames, opposed conclusions — a genuine fork
Description

shell is 30 files / ~2,046 LOC with 11 public exports spanning app chrome, both home screens, settings, update UI, and theming — nearly double the next-largest module, and the default destination for every new screen. Two frames drew opposite conclusions, and both are defensible. Option A — mode as the axis: split out a mode module owning ModeGate/FirstRunChooser/switching, give each mode's home its own module, leave a thin frame; "which mode does this belong to?" becomes the placement rule for the next three screens. Option B — delete mode: treat provider/client as a property of data, not the device — one home with "Today" (appointments you own) and "Yours" (appointments you received), empty sections collapsed; the first booking or first imported link becomes onboarding. B also fixes the worst first-run moment: a stranger opening an import link being asked to declare an identity before seeing their appointment.

Basis

direct: the export list and ModeGate.tsx:18-19 verified line-exact; project memory records "providers are also clients; mode not locked at onboarding" — the north star both options serve. Caveat from verification: whether /import itself sits behind ModeGate was not traced; confirm before weighting B's onboarding argument.

Rationale

A module that is the default destination is a namespace, not a module. The product's core user is one human who is both provider and client; mode currently has no first-class home in the code (A) — or arguably shouldn't exist at all (B). Whichever way it goes, the decision determines where epic #5's screen and every subsequent screen lands, so it is cheapest to make now.

Downsides

Option B reworks a concept shipped three days ago and needs careful UX for the pure-provider majority. Option A is a large mechanical refactor with no user-visible payoff of its own. Ranked last not because it is weak but because it is the biggest decision with the least external forcing function.
